# Operator-installed plugins and colour packs

M8 adds trusted, in-process Python plugins. Installation belongs to the operator: there is no upload endpoint or marketplace. Honest plugins use the permission-checked host API; Python code is not sandboxed. Review the source before installing it. Plugin code can otherwise access the process, its environment and its database directly.

Put a pure-Python folder in `SPUNTO_PLUGINS_DIR` (default `$SPUNTO_DATA_DIR/plugins`). Its `plugin.toml` uses API `1.0` and an entry such as `plugin:plugin`; `plugin.py` exports the matching `spunto.host.Plugin`. Relative imports work inside a private namespace, without adding the folder to the process's import path. Installed packages in a derived image register an entry in the `spunto.plugins` group pointing to `package.module:plugin` and ship `plugin.toml` beside that module. Discovery reads metadata; code imports only when the plugin is enabled. Installation and updates require a server restart.

The reviewed plugin contract supports API `1.0` and retains first-party `0.4` and `0.9` compatibility. This contract approval does not certify arbitrary third-party code or replace the required runtime harness and deployment checks. Unsupported versions, unreadable manifests and conflicting IDs appear as separate Failed cards. Built-in IDs cannot be replaced. An error in one operator plugin does not prevent server startup.

Removing an operator folder/package requires a restart. Its retained catalog card becomes Removed/Off: code, commands, settings forms and enable actions are unavailable while stored data and plugin-authored notes remain. The card reports actual Built-in/Operator-installed/Unknown origin; older metadata can honestly remain Unknown. `SPUNTO_PLUGINS` still locks a known missing ID, but missing code cannot activate; an unknown ID is a configuration error. Use the card's web Stored data action for an explicit owner-session cleanup. The confirmation uses real scoped counts, keeps notes, and leaves the Removed card at zero data; an environment lock does not prohibit cleanup. Android opens the same-root web owner-sign-in page for this action, without passing a device token in a URL. Changing a plugin's registered folder/entrypoint source identity under the same ID clears prior grants and requires fresh approval. Folder identity follows its resolved folder path; entrypoint identity follows its distribution/name/value registration. This mechanism does not hash Python file contents.

Run `spunto plugin check <folder>` before installation. This checks TOML, permissions, contribution budgets, API compatibility, the local entry path and Python syntax without importing code, opening a database or requiring server configuration. Runtime handlers and payloads must also pass the real-SQLite `spunto.host.testing` harness. The example in `examples/plugins/word-count` demonstrates a stored panel and the same async API as bundled plugins.

Restart the server after adding, changing or removing a colour pack, then refresh/sync clients to obtain its validated catalog. Previously cached tokens remain available offline. Colour packs live in `SPUNTO_THEMES_DIR` (default `$SPUNTO_DATA_DIR/themes`). Each folder has `plugin.toml` with `kind = "theme"`, an ID, name, version and `tokens = 1`, plus `theme.toml` with `[light]` and `[dark]`. Both modes supply the sixteen `#RRGGBB` roles: `paper`, `raised`, `sunken`, `ink`, `ink-2`, `ink-3`, `rule`, `rule-strong`, `field`, `accent`, `accent-strong`, `accent-soft`, `on-accent`, `highlight`, `danger` and `warn`. Optional `[accents.<id>]` entries have a name and light/dark accent-role overrides. Every resolved mode/accent must pass contrast validation. Extra TOML keys are ignored; packs cannot load code, fonts or layout rules. Invalid packs have a disabled card naming the failing pair or field. The five built-in IDs and their default tokens are unchanged.

The client manifest gains `theme_catalog`, an array of cards with `id`, `name`, `status` (`available` or `failed`), optional `reason`, `tokens: 1` and `accents`. Available cards also contain complete `light` and `dark` token maps; accent entries have `id`, `name` and complete resolved `light`/`dark` maps. Each explicit accent supplies `accent`, `accent-strong`, `accent-soft` and `on-accent` in both modes. The picker shows an Accent row when `accents` has at least one explicit entry, alongside a separate Default/null choice; the five built-ins have no extra entries. The selected `theme` remains `{id, tokens, light, dark}` and additionally carries `accent` when selected. Instance preferences add `theme_accent`, a nullable accent ID; `null` chooses the pack's default. A missing or failed saved pack resolves to Carta while its stored owner preference remains recoverable.

Anyone may GET `/api/v1/themes/{id}.css`, optionally with `?accent=<id>`. The server generates only validated, scoped colour variables. Responses carry an ETag of their exact bytes and `Cache-Control: no-cache`; a matching request returns 304. Unknown or failed packs and unknown accents return 404. Clients cache the manifest tokens for offline use. Appearance code and device overrides remain client-owned.

The optional manifest `needs` list contains `{setting, reason}` entries naming declared settings. Empty requirements leave a switched-on plugin Waiting with that sentence; secrets still come only from the environment. A plugin can call `await ctx.report_status(stable_code_or_none)` to report a bounded lowercase status code under its current generation and writable credential. It cannot change lifecycle state through this call.

Email in requires an explicit `imaps://host[:port]`, username, folder and allowed From addresses; `SPUNTO_PLUGIN_EMAIL_IN_PASSWORD` (or `_FILE`) supplies its password. Telegram requires numeric account IDs and `SPUNTO_PLUGIN_TELEGRAM_BOT_TOKEN` (or `_FILE`). Both are off by default, create notes with `origin=external` and `machine=false`, and cannot read existing notes. An email address allowlist is a filter on the From header, not proof of sender authenticity. Telegram accepts private chats with matching sender/chat ID and a non-bot sender. These plugins send no replies or notifications.

IMAP uses verified TLS with hostname SNI and pins validated DNS answers to numeric TCP connections. Explicitly configured private LAN addresses are allowed; loopback, link-local, metadata and the server's own destinations are blocked. `ctx.imap_read` exposes only read-only SELECT, UID SEARCH and bounded BODY.PEEK, through the plugin's small thread pool. It allows five messages of at most 256 KiB each, with a 35-second async deadline and socket/operation deadlines inside the worker. Cancellation prevents subsequent local writes; an already running Python thread can finish its bounded protocol operation. Raw IMAP errors and its debug ring are suppressed; owner status contains stable codes.

The worker checks its absolute deadline before and after every socket receive/send, including fragmented lines and literals; a peer cannot prolong the job by trickling bytes. Server-owned hostnames are resolved and their addresses are denied even through another hostname. MIME parsing and HTML extraction run off the event loop in the same bounded plugin pool. New invalid configured destinations are rejected before storing settings; legacy invalid destinations remain visible as Waiting without preventing startup.

Polls are persistent jobs, normally one minute apart. UIDVALIDITY/UID and Telegram update IDs advance after successful per-message note creation (or an explicitly ignored disallowed sender). Stable note receipts make retries after a checkpoint-write failure idempotent. The host's five-per-day unattended creation budget applies to each plugin; a budget stop leaves the next message pending and retries hourly. Oversized or unsupported text/media remains at its checkpoint with a status code, for the operator to resolve in the mailbox or bot client. Email prefers plain text, extracts visible text from HTML without scripts/styles, and never loads remote content. Telegram preserves text or captions. Attachment-only messages require operator resolution; neither plugin has attachment grants, and neither silently truncates words.

`ctx.notes.create(..., request_id=...)` returns the new note on its first successful call. A replay returns the immutable creation acknowledgement (`id`, initial `version`, `created_at`, `origin`, `machine`, `replayed: true`), without current body or flags. Existing older receipts guarantee only `id` and `replayed`. Replays do not resurrect deleted notes or consume the daily creation budget again, and they remain successful after the owner edits, hides or trashes the note. Call `ctx.notes.get(id)` separately when a current note is needed; its read permission and privacy checks still apply. Ask, Digest, Develop and Translate use only the acknowledged ID; the importers' ordinary creates use no request receipt.

## Context packs

Enable **Context packs** in Settings → Plugins. Open its command from the web palette, the composer's `/` menu or a note's actions; Android uses the `/` menu and note actions. Start a pack with a title, project, goals, constraints, decisions and open questions. These are your own words: the plugin works with AI off and never drafts or rewrites the brief automatically. Reopen saved packs from **Context packs**, then use **Edit brief** to change or delete one. A concurrent edit asks you to reopen rather than overwriting the other edit.

Use **Review sources** to search or browse notes, select a note by title, or remove a selected source. A pack supports up to ten source notes and a complete Markdown brief of at most 4,000 characters; each curated section allows 500 characters. The pack stores IDs and revision baselines rather than source-body snapshots. The brief reports whether a source's current revision changed or the note became unavailable. **Acknowledge all current source revisions** explicitly updates those baselines while retaining your prose. Remove unavailable sources before acknowledging the remaining ones.

Use **Copy** to put the displayed Markdown on the clipboard. **Keep private note copy** saves an ordinary private note for normal sync, offline reading and export; it is a snapshot and later pack edits do not update it. This action requires current source baselines. Retrying it returns the original copy; a trashed or unavailable copy is not recreated. Pack editing and source review require a connection: plugin records themselves are not an Android offline replica.

Agents with read access can discover `context-packs_list` and `context-packs_get`; the latter accepts `pack_id`. Both recheck source visibility and the token's private/external permissions. A hidden or unavailable source hides the whole pack from that token, including its curated prose. Private and external content classifications remain set after source refresh or removal; removing an unavailable source conservatively retains both. Review the brief and its classifications explicitly before clearing either in **Edit brief**. Copying text out of the app is an explicit export. Deleting a pack keeps existing note copies and a content-free digest receipt that prevents a delayed creation retry from recreating it.

## Decision journal

Enable **Decision journal** in Settings → Plugins. Use **Record decision** from the web palette, the `/` menu or a note's actions to record a title, the decision, alternatives considered, rationale and expected outcome. An optional review date uses `YYYY-MM-DD`; choose **Private** when appropriate. Starting from a private source also makes the created note private. The result is an ordinary owner-authored note, with a link to the optional source and the time it was recorded. It syncs and exports normally and needs no AI service.

Find entries in the **Decisions** view or through the **Decision journal** command. Open a decision and use **Review decision** or the panel's **Review or reopen** action to record what happened, an optional reflection and the next review date. Choose `reviewed`, `closed` or `open`; `open` reopens the decision and asks you to record why. Every outcome is a separate dated note linked to the original, so later reviews retain the original decision, alternatives and reasoning. The journal can page through earlier outcomes. Concurrent or interrupted reviews preserve the pending review for an explicit resume instead of replacing it.

Recording and reviewing need a connection. Synced decision/outcome notes, the Decisions view and stored panel information remain readable offline; online action buttons are unavailable then. Review dates supply a due status, not scheduled reminders or notifications. The journal adds no plugin MCP tools; agents use the ordinary note search/read tools subject to each note's current permissions. There is no automatic AI evaluation or outcome generation.

## Smart tag suggestions

**Label suggestions** runs after a note is saved when a chat model is available. It proposes at most three labels, including at most one new label. To apply the agreed automatic-tagging policy, enable **Accept existing labels automatically** in its settings and choose **Minimum confidence for automatic acceptance** (default `0.9`, configurable from `0.7` to `1.0`). Only labels already in use can be applied automatically at that threshold. New labels always wait for review. The setting starts off, and an existing owner's explicit opt-out is preserved.

Suggestions use your vocabulary and live examples of how you tagged owner-authored notes, rather than label names alone. Semantic neighbours supply examples when embeddings are available; tagged notes from the vocabulary fill gaps and support chat-only installations. The plugin reads the most recent 60 of its labeling decisions and uses at most six accepted/dismissed feedback items as contextual evidence. A rejection on the current note remains an exclusion; a rejection on another note is not a universal ban. This is bounded context selection, not a globally trained personal model or a review of the entire library.

At most four past usage examples and six past notes in total enter a call. The gateway rereads their current content and bounds the target to 8,000 characters and each past note to 2,000, within a shared 20,000-character note-text budget. Past examples exclude private, trashed, machine-written, agent and external notes; current visibility and revisions are checked again before suggestions or automatic applications are committed. Note text reaches the configured chat profile through the gateway's data fences. Private and machine-written target notes are skipped, as are notes shorter than three words.

Use **Suggest labels** in a note's actions to run labeling now, including when the text has not changed. It retains the owner's confidence setting, existing-label-only automatic acceptance and remembered refusals. Saved labels remain ordinary note text and history; there is no separate tag-training database.

Neighbour lookup is optional: while an embedding index is preparing or its provider is unavailable, label suggestions can still use the current vocabulary and tagged examples through the chat model. Invalid vector output and privacy refusals still fail closed. An outage on a profile shared by chat and embeddings may pause both capabilities until its backoff expires.

## Link notes and review text changes

**Link to note** starts with recent note titles and a search field. Choose a matching title, then review and apply the proposed link. Numbered captions distinguish matching titles; note identifiers and revision mappings stay internal to the form. Searching does not edit either note. A changed source or selected destination asks you to reopen the chooser, and an existing link is not proposed again. Direct API callers may continue supplying `target_id`.

**Tidy text** returns a comparison focused on changed lines with a small amount of surrounding context. **Apply changes** accepts the full proposed body at its original note version. Long-line results direct you to Review for the full comparison. Labels, links and meaning remain guarded; running Tidy never silently edits the note.

## Model choices, waiting states and recovery

The space owner can choose chat, embedding, vision and transcription models in the server's web **Settings → AI**. Provider URLs, credentials and request limits remain environment settings. Saved space choices override environment defaults; **Use environment defaults**, followed by **Save models**, resets them. A plugin's explicit profile route still takes priority over the default binding, so check that route when a plugin appears to use another profile. See [AI operations](operations.md#ai-profiles-and-index-recovery).

A Waiting plugin names the missing capability, attachment support or setup requirement. A failed connection check includes its safe operator hint. Command failures distinguish invalid model answers, unavailable indexes, credentials, missing models, timeouts and provider limits while retaining stable API error codes. Server plugin warnings include the plugin, operation, exception class and a database SQLSTATE when available; exception messages, note text, provider response bodies and credentials are omitted.

After repairing a provider or upgrading the server, use the failed plugin card's **Retry** action to re-enable it. The supported API equivalent is `POST /api/v1/plugins/{id}/enable` with the exact current manifest `permissions` array, authenticated as an owner session or device; cookie requests also need the matching Origin. This resets the circuit counter and retries retained dead work without deleting plugin data or suggestions. A restart alone preserves a Failed state. Do not edit lifecycle rows directly.

## Periodic tag curation

Enable **Label gardener** with chat and embedding profiles available. Its settings choose the weekly day and time, initially Sunday at `18:00` in the instance's time zone. **Review tags now** in the web palette or the `/` menu starts an immediate pass. Scheduled and manual runs share the same limit: at most three pending proposals and three proposals created per week. Dismissing a proposal does not grant another weekly slot, and a refused change is not offered again.

Each pass samples up to 500 recent eligible non-private, non-machine notes and up to 50 top labels from a vocabulary limited to 500 labels. It supplies bounded labeled and unlabeled evidence, with full evidence notes no longer than 20,000 characters each and a combined 50,000-character note-text budget. The command reports its sample coverage. This is not a full taxonomy audit: absence from a sample does not prove a tag is unused, and sampled note-creation dates are not a history of when tags were added.

The gardener can propose a clearer new name, merge a tag into an existing tag, remove a misleading or redundant tag, or add a new tag to a cluster of two to ten supplied unlabeled notes. Every cleanup and cluster proposal goes to the shared **Review** screen; none applies automatically. Review the reason and affected-note count before applying. Removing a tag removes its parsed tag occurrences, not the notes, and accepted changes use ordinary note revision history.

Global tag changes are applied from an owner session in web **Review**. Android shows the proposal and offers **Open web Review**, which requires owner sign-in and a connection; it does not apply global cleanup offline. Use the updated APK for correct removal wording: removal proposals carry a null destination, which older Android builds may display as a rename instead.

## Additive Host API 1.0 helpers

`ctx.storage.records.compare_and_set(collection, id, expected_data, data, *, note_id=None, key=None)` replaces a record only when its current JSON matches `expected_data`; `None` requires an absent record. `compare_and_delete(collection, id, expected_data)` deletes only a matching existing record. Both return a boolean and perform the comparison and write in one transaction. JSON object key order does not affect equality. `records.list(..., after=id)` adds an exclusive cursor to the existing ascending record-ID order. These calls retain plugin namespaces, generation/write-scope checks and the 64 KiB value limit; plugins still run no SQL.

A manual plugin may declare `creates = "owner"`. Its notes carry `origin=owner`, `machine=false` and the plugin source, and creation is restricted to explicit commands from an owner session or device. This mode rejects AI permissions, `notes.update_own`, unattended creation and importer/source/initial-flag overrides; `private` remains an explicit boolean. Pass `source_versions={note_id: version}` when deriving a note from selected sources: the host checks visibility and versions atomically with creation and refuses a public result if any source is private. Later changes to owner-authored notes use ordinary owner edits or reviewed suggestions, never a plugin's `update_own` shortcut.

## Thinking desk

Enable the optional **Thinking desk** plugin to follow a topic through selected notes in creation order, or to intentionally combine notes from different subjects. History records your directed **builds-on**, **challenges**, and **replaces** connections; originals stay intact. Collision supplies creative prompts and an editor for your own idea, with no AI or external processing. Both workflows offer a reviewed private note snapshot. Commands need a connection; saved snapshots are ordinary notes that Android can sync for offline reading. Changed sources require explicit review before saving another snapshot. See the [Thinking desk contract and acceptance steps](decisions/2026-10-31-thinking-desk.md).
